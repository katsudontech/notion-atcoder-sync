題材：[ABC479 D - Back and Forth Distance](https://atcoder.jp/contests/abc479/tasks/abc479_d)
「DPを回す順番がわからないのでメモ化再帰で書いたが、TLEになった」という経験からの整理。改善後のループDPはユーザーがACを確認した。
**メモ化再帰は計算順を任せられるが、状態設計・遷移の計算量・再帰の深さまで自動で解決してくれるわけではない。** 自然な再帰を書いてから、重複している処理を見つけて改善する進め方でよい。
## @cache が保存するもの
保存するのは「引数 → 返り値」の対応だけ。ローカル変数の value や rest は保存しない。同じ引数で再び呼ぶと、関数本体を実行せず返り値を返す。
関数の中で同じキャッシュ付き関数を別の引数で呼べば、その呼び出しの返り値も別に保存される。「範囲の最小値もメモ化する」とは、範囲の最小値を返す関数を用意するという意味。
入力配列など、返り値が依存する外部データを途中で変更すると、引数が同じでも古いキャッシュが返ることに注意する。
## なぜ元のコードはTLEになったか
元の定義は solve(s, direction)：sから指定した方向の目的地へ移動する最小コスト。この自然な定義から始めてよい。
左方向では、次のように右側の候補を全部調べていた。
```python
for i in range(s + 1, N):
    mins.append(solve(i, left) + R[s])
```
メモ化により各状態の本体は1回しか計算しなくても、その1回の中に長いループがある。状態数O(N) × 1状態あたり最大O(N)で、全体は最悪O(N² + Q)。キャッシュ済みの関数を呼ぶ回数も計算量に含める。N ≤ 300000では厳しい。
分類：計算量／DPの遷移の工夫。
## 「i以上の最小値」はどう思いつくか
最初から思いつく必要はない。隣の状態で、ほぼ同じ候補を調べ直していないかを見る。
R\[s\]はループ中一定なので、必要なのは「R\[s\] + sより右にあるsolveの最小値」。
```plain text
s = 0：solve(1), solve(2), solve(3), solve(4) の最小値
s = 1：          solve(2), solve(3), solve(4) の最小値
s = 2：                    solve(3), solve(4) の最小値
s = 3：                              solve(4) の最小値
```
下の行の最小値がわかれば、要素を1つ足すだけで上の行も求められる。そこで補助状態を追加する。
```plain text
suffix_min(i) = i以上のsolve(j, left)の最小値
suffix_min(i) = min(solve(i, left), suffix_min(i + 1))
suffix_min(N) = INF（空範囲）
```
元のsolveの定義を捨てるのではなく、繰り返し使う集計を別の状態として保存する。会話中のbestは、この補助状態とsolveの計算を1つにまとめたもの。
合言葉：**隣の状態を計算するとき、ほとんど同じ候補を調べ直していないか？** 重なっている範囲の最小値・最大値・合計を使い回せないか考える。
## DPの順番は参照先から決める
移動したい方向ではなく、必要な状態を先に確定できる順番で決める。

ユーザーがACした前計算部分。Lは先頭にINF、Rは末尾にINFを入れた0-indexed配列。left = 0、right = 1。
```python
dp = [[INF] * 2 for _ in range(N)]

nowmin = INF
for i in range(N):
    # 更新前：j < i の dp[j][right] の最小値
    dp[i][right] = min(nowmin + L[i], R[i])
    nowmin = min(nowmin, dp[i][right])

nowmin = INF
for i in reversed(range(N)):
    # 更新前：j > i の dp[j][left] の最小値
    dp[i][left] = min(nowmin + R[i], L[i])
    nowmin = min(nowmin, dp[i][left])
```
自分のDPを計算した後でnowminに自分を加える。これで次の状態でも「参照したい側だけの最小値」という意味が保たれる。前計算O(N)、各クエリO(1)、全体O(N + Q)、空間O(N)。
## メモ化再帰でも再帰の深さは別問題
補助状態をメモ化すれば計算量はO(N)にできるが、i → i + 1 → i + 2のような依存では再帰がO(N)段になる。
sys.setrecursionlimitは上限設定であり、スタック領域を増やす設定ではない。元のCPythonのREは深い再帰が有力だが、提出のエラー詳細を未確認なので原因は断定していない。

キャッシュを参照先から順に埋めれば深い再帰は避けられるが、結局その方法では計算順を指定している。「順番を考えずに書ける」という利点と、実装上の制約は分ける。
## 次に使う手順
1. 自然な状態定義で再帰・漸化式を書く。
2. 状態数と、各状態で調べる候補数を数える。
3. 重なった範囲を何度も走査していたら、集計用の補助状態を考える。
4. 再帰の深さを確認する。
5. ループに直すときは「参照先が先に確定する順番」を選ぶ。
**メモ化再帰を選んだことが失敗ではない。返り値の再計算と、候補の再走査は別の重複だと気付くことが今回の学び。**
